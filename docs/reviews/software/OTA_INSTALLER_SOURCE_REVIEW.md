# Independent source review: SDK OTA installer study

Reviewed 2026-10-24: `firmware/ota_study/main/ota_installer.h/.c`, against the pinned ESP-IDF v6.1 source (`fff9895c82d744c7237be8847347bdd1b07c6643`). Source review only; no physical flash, radio, device, SDK rebuild, provisioning or production edits.

## Finding corrected during review

**P2: failed esp_ota_begin can leave an allocated SDK handle without cleanup.** In the pinned `components/app_update/esp_ota_ops.c`, `esp_ota_begin` registers the OTA entry and writes `*out_handle` before erasing the target partition. An erase error returns directly, without removing that entry. The reviewed installer sets `handle_active` only after ESP_OK, so its `fail()` path skips `esp_ota_abort` when begin returned an error after allocation. This leaks the registered operation and reports `cleanup_unknown == false` despite an active SDK entry. The author and independent shim reviewer were notified immediately. Recommended regression distinguishes failure before allocation from failure after output-handle publication and models abort failure separately. **Corrected in production source during review:** begin now starts from sentinel handle 0, tracks a nonzero published handle on either SDK result, aborts it on failure and latches cleanup ambiguity if abort fails. Successful SDK begin with no handle is also rejected. The pinned allocator issues incrementing nonzero handles from 1; the explicit one-installation-per-boot/exclusive-OTA-owner contract excludes wrap and other active owners. Source fix reread. Reran the stable dedicated harness: `python3 -m unittest discover -s tests -p test_ota_installer.py -v` PASS (one Python test compiles/runs eight C groups with ASan/UBSan). Regression covers pre-allocation failure, post-allocation failure requiring abort, and abort failure latching cleanup unknown. **No unresolved concrete finding remains in this review.**

## Other checks

The trusted manifest verifier is mandatory, not a decoded-wire boolean, and no target crypto implementation or production trust provisioning is implied. Plan bounds/version are checked before flash entry. Authorization is checked before/after potentially blocking verification, partition checks, begin/write/end and readback. Stale lease is rejected before calling clock/authorization, so it cannot expire the current installation. Busy protects synchronous callback reentry; single-owner serialization and exclusive authority over all OTA/partition writers remain explicit preconditions.

Partition checks require canonical existing aligned OTA0/OTA1/data extents, pairwise non-overlap, running app in OTA0/1, boot equal to running and running state VALID. The selected target must be the opposite OTA slot and have enough capacity. Checks repeat during writes and before selection. No factory/running partition erase path was found. SDK begin itself may update inactive OTA metadata as part of its rollback bookkeeping; separate final selection does not mean begin is a read-only metadata operation.

Writes require strict offsets and bounded nonzero chunks, exact expected total before finish, and no blind retry after failure. Pinned SDK end removes its registered entry on every result for an existing handle, consistent with consuming the handle before `esp_ota_end`. Readback hashes actual partition bytes in bounded chunks, checks exact SHA256 and app descriptor/version/secure-version floor, and repeats the hash before boot selection. PSA operations are aborted on error and after finish; cleanup failure latches unknown state. Clock regression, idle and absolute deadlines fail closed; clock is sampled again after I/O.

The installer latches `selection_may_have_changed` before calling the SDK setter; failure or loss of maintenance authority afterwards cannot falsely claim no selection change. Selected/fault states do not allow retry. No reboot, health confirmation or durable release-counter advancement is performed. SDK image validation is used; this is not a declaration that Secure Boot signing/provisioning, end-to-end antirollback, power-loss recovery or physical bootability has been qualified.

The rerun also covers partition guards, strict offsets, stale leases, revocation/time advancement around I/O, PSA cleanup/read errors and changed-byte/ambiguous selection paths. Its hash double is explicitly NONCRYPTO, with fixture equality and digest mismatch checks; it does not substitute for PSA SHA256 qualification. Independent shim/behavior test evidence is maintained separately in `docs/reviews/software/OTA_INSTALLER_REVIEW.md`; a modelled PSA hash is not proof of SHA256 execution or physical flash behavior.
